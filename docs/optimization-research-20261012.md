# Производительность: исследования и проверяемые изменения

## Исходное состояние

Журнал запуска 21:48 11 октября подтверждает нативный Vulkan и NVIDIA RTX 3050 6GB Laptop. Активный профиль включает ZakoOptimization; Motion Blur и Far выключены. Нового JFR после 2 октября в игровом каталоге нет. Причина разницы между сообщёнными пользователем 800 и 500 FPS пока не установлена. Настройки качества и лимит кадров не менялись.

## Изученные подходы

- [Sodium](https://github.com/CaffeineMC/sodium): системное изменение рендера и пакетная обработка геометрии. Полная замена backend требует отдельной проверки совместимости, не равна одному ускоряющему флагу.
- [ImmediatelyFast, ветка 26.2](https://github.com/RaphiMC/ImmediatelyFast/tree/26.2): уменьшение количества draw/upload операций. Изучен enhanced_batching/RenderTypeFeatureRenderer_Group. Принудительная перестановка всех групп не перенесена: порядок прозрачных элементов требует проверки. Применён общий принцип объединения работы к собственному HUD Vela.
- [FerriteCore: описание алгоритмов](https://github.com/malte0811/FerriteCore/blob/main/summary.md): дедупликация данных моделей/состояний. Приведённые там объёмы памяти относятся к старым модпакам; эти цифры нельзя переносить на Vela 26.2. Проверены собственные владельцы временных и кэшированных данных.
- [Lithium](https://github.com/CaffeineMC/lithium): набор независимых оптимизаций игровой логики. Клиентское изменение не ускоряет тики чужого сервера.
- [ModernFix](https://github.com/embeddedt/ModernFix): загрузка, память и исправления. Совместимость исследованных веток с 26.2 не подтверждена, код не переносился.
- [EntityCulling](https://github.com/tr7zw/EntityCulling): асинхронная проверка видимости, ограничения для нестандартных границ моделей. Текущая лицензия ограничивает распространение; код/JAR не включены. Видимую толпу такая оптимизация сама по себе не устраняет.

## Изменения этого этапа

1. Workers.Stream публикует модели пакетами по восемь вместо отдельного Future на каждую. Барьеры await/finish обязательно отправляют остаток и дожидаются завершения; ошибки возвращаются вызывающему коду.
2. Native-страницы моделей перестали сохранять максимальный объём за весь сеанс: пятисекундные окна спроса позволяют освобождать лишние страницы между кадрами. После окна без работы освобождаются также сохранённые задания/развёртки моделей.
3. Временные Quaternionf, Vector3f и указатель обхода модели переиспользуются отдельно для каждого рабочего потока.
4. Композиция кэшированного HUD встроена в обычную GUI-пачку. Порядок: живые camera overlays/crosshair → кэш ванильного HUD → живые элементы Vela. Между слоями используются native strata. Убраны отдельный composite render pass и дополнительный вызов GuiRenderer.render.
5. Профиль нагрузки дополнен GCHeapSummary/PhysicalMemory. Начало/конец замера записывают разрешение, Java heap, активность путей Zako и объём native-страниц моделей. Никакой постоянной записи и сетевой отправки нет.

## Проверка и ограничения

Автотесты покрывают пакетирование, однократную обработку каждого индекса, завершение короткого остатка, ошибки workers и сокращение рабочего набора. Сборка и статический анализ mixin не подтверждают GPU-результат. Визуальная проверка нового HUD-прохода и A/B-профиль ещё нужны.

Протокол: одинаковая точка и настройки; `/vela perf start profile`, 15 секунд стоять, 60 секунд идти одинаковым маршрутом, `/vela perf stop`. Повторить с ZakoOptimization выключенным. Не менять F11/Alt+Tab/разрешение во время записи. Сравнивать среднее/p95/p99, GC и нагрузку, не только максимум FPS. Рост FPS и снижение загрузки CPU/GPU одновременно не гарантируются: без ограничения FPS освободившийся ресурс может уйти на дополнительные кадры.
