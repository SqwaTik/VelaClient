# Оптимизация 3.0

## Изменения

- Встроенный оптимизатор больше не регистрируется как модуль. Он не участвует в поиске функций, избранном, биндах и переключении модулей. Внешний ZakoOpt по-прежнему отключает встроенную интеграцию во избежание дублирования.
- Параметры хранятся в поле `optimization` профиля. При первом чтении старого профиля они копируются из `modules.zako_optimization.settings`. Старый блок сохраняется для отката; его настройки обновляются при сохранении. Старые `enabled` и бинд не управляют встроенным оптимизатором.
- Запись неизменных настроек в общие объекты рендера больше не выполняется каждый кадр. Проверка изменений не создаёт новых объектов; при изменении параметров или смене экземпляра владельца значения публикуются повторно. Проверки совместимости и отказов рендера продолжаются каждый кадр.
- Стеклянные волны проецируют 195 общих вершин вместо 512 повторных вершин полностью видимой волны. Число сегментов, UV, порядок квадов и перспектива сохранены. При частичном отсечении прежний алгоритм мог выходить раньше; указанное сокращение относится к полностью видимой геометрии.

## Исследованные подходы

- [ImmediatelyFast](https://github.com/RaphiMC/ImmediatelyFast): пакетная отправка геометрии и эффективные буферы. В клиенте уже есть пакетный рендер частиц и собственные буферы; параллельная реализация не добавлялась.
- [EntityCulling](https://github.com/tr7zw/EntityCulling): асинхронное определение невидимых объектов. Не переносилось без проверки взаимодействия с подсветками, отображением сквозь стены и текущим отсечением.
- [Lithium](https://github.com/CaffeineMC/lithium): оптимизация игровой логики с сохранением поведения. Серверные оптимизации не ускоряют удалённый сервер со стороны этого клиента.
- [GPUOpen RDNA Performance Guide](https://gpuopen.com/learn/rdna-performance-guide/): управление ресурсами и синхронизацией. Рекомендации изучены как архитектурные ориентиры, не как доказательство ускорения RTX 3050.

Новый сторонний код из этих проектов не копировался. Существующие уведомления и лицензии ZakoOpt сохраняются.

## Проверка результата

### Кэш подготовленного текста

Второй проход: поиск по существующему текстовому кэшу использует повторно один
временный ключ под прежней блокировкой. После поиска ссылки освобождаются,
в карту попадают только неизменяемые ключи. Сохраняются лимит 2048 записей,
LRU, сброс при перезагрузке ресурсов и обход кэша для §k.

Проверяемая гипотеза: новый ключ на каждом попадании создаёт ненужный мусор.
Изолированный тест на Java 25 после прогрева, 100000 успешных поисков:
старый путь — 4000104 байт выделений, новый — 0 байт по ThreadMXBean.
Это не измерение FPS и не оценка экономии памяти всего Minecraft.

Дополнительно изучены [подходы FerriteCore](https://github.com/malte0811/FerriteCore/blob/26.1/summary.md)
к уменьшению памяти и [рекомендации Oracle по JFR](https://docs.oracle.com/en/java/javase/22/troubleshoot/troubleshoot-performance-issues-using-jfr.html).
Исторические цифры FerriteCore не перенесены на нашу сборку; мод не добавлялся.
Доступные локальные игровые JFR-записи относятся к сентябрю и не доказывают
эффективность текущего октябрьского клиента.

Автотесты проверяют отсутствие повторных публикаций, восстановление параметров при смене владельца, миграцию профилей, отсутствие модуля в реестре и совпадение вершин с прежним алгоритмом при разных положениях камеры.

Игровой прирост ещё не измерен. Сравнивать следует одинаковую сцену, разрешение, дальность и набор эффектов: `/vela perf start profile`, одинаковый маршрут, `/vela perf stop`. Оценивать среднее время кадра, p95/p99 и паузы GC. Эти изменения не являются доказательством радикального увеличения FPS.
