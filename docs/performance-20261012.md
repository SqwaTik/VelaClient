# Замер 12 октября и снижение временных выделений

## Данные

Локальный профиль `vela-1791811660031.jfr`, 16:26:22–16:27:40 МСК, 78 секунд.
Тестировался JAR SHA256 `F9DFEE5E8BEA12E5401156C4C0CB653F22E12785EE5AE38F8762C42BFF398795`.
1920×1080, Zako включён. Пользователь сообщил об открытии GUI около 10–15-й секунды.
Сравнительной записи с Zako выключенным нет, поэтому причинный прирост пока не измерен.

- 40363 кадра: среднее 1,73 мс, p95 2,67 мс, p99 3,38 мс, максимум 88,60 мс.
- 6 кадров дольше 16,67 мс; после атак 568 кадров, максимум 6,82 мс.
- GC pauses: 62,0; 41,4; 24,6; 26,1; 26,5 мс. Четыре больших frame events совпадают с GC; остальные причины не установлены.
- Паузы на 40-й, 56-й и 72-й секундах нельзя списать только на GUI в начале.
- Execution samples: GuiRenderState.hasIntersection 127/1106 Java samples; это не процент GPU-времени и не доказательство равномерной нагрузки по всему тесту.
- Allocation samples показывают повторные Matrix4f и ChunkSectionLayer.values в prepareChunkRenders, boxing Integer при GUI-сортировке, работу с текстом табличек. Веса JFR являются оценкой, не точным счётчиком выделений; крупный sample classfile/lambda bootstrap нельзя считать постоянной нагрузкой без временного анализа.

## Что меняется

1. TerrainAllocationMixin: один snapshot modelView на вызов prepareChunkRenders и приватный read-only массив слоёв. ChunkSectionInfo читает Matrix4fc синхронно при записи uniform-данных. Snapshot не переживает вызов, поэтому движение камеры и смена мира не требуют инвалидирования общего кеша. Геометрия, прозрачная сортировка, время появления чанков, освещение и список видимых секций не кешируются дополнительно и продолжают обновляться штатно.
2. GuiSortAllocationMixin: primitive int comparisons вместо boxing. Прежний порядок scissor → pipeline → texture, null-first и равные ключи сохранены. Оба новых hook включаются существующей настройкой microOpts в Zako; выключение возвращает исходный путь.
3. Far.active читает тот же экземпляр модуля из VelaServices напрямую, без синхронизированного поиска по строковому идентификатору при каждом запросе чанка.

## Почему не добавлен второй кеш блоков

Minecraft 26.2 уже хранит SectionMesh и GPU-буферы, а prepareChunkRenders готовит команды для видимых секций. Кешировать итоговые команды без учёта перераспределения GPU-буферов, камеры, прозрачности и изменений секций небезопасно. На этом этапе устранены повторные неизменяемые данные внутри подготовки кадра.
Дополнительно изучена архитектура [Sodium ChunkRenderer](https://github.com/CaffeineMC/sodium/blob/dev/common/src/main/java/net/caffeinemc/mods/sodium/client/render/chunk/ChunkRenderer.java); текущая dev-ветка не использовалась как совместимый исходник для 26.2.

## Проверка

Сборка `test build sourceBundle` и 247 тестов проходят. Новые проверки: соответствие hook фактическому bytecode 26.2; read-only тип матрицы uniform; равенство scissor-сортировки на 7056 парах, включая null и совпадающие ключи; единство экземпляра Far в реестре и прямом доступе.
Реальное применение mixin и прирост нового JAR требуют запуска пользователем. Игра агентом не запускалась. Настройки качества, GC и лимит FPS не менялись.

Следующий замер: одинаковая сцена и маршрут, `/vela perf start profile`, 15 секунд стоять, 60 секунд двигаться, `/vela perf stop`. GUI во время этой записи не открывать; его можно измерить отдельной записью. Сравнить GC pauses и распределение кадров с этой базой, а не только максимум FPS.
